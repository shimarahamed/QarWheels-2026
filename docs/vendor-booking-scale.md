# Vendor booking scale sidecar (5k DAU)

Scope: mobile vendor booking reads and their exact dashboard totals. This is independent of staff assignment; assignment changes may update a booking row but must not define inbox membership or aggregate scope. No executable change is made here.

## Findings

1. `mobile/lib/firestoreOps.ts:759-844` installs one `onSnapshot(bookings where businessId == claim.b [and branchId == activeBranchId])` in `mobile/app/vendor/_layout.tsx:27`. There is no status, date, order, or limit constraint. The callback maps and sorts **every** returned document on every snapshot, then `mobile/lib/store.ts:617-620` replaces the entire array. Thus a selected branch with N lifetime bookings costs N document reads on a fresh server listen and O(N log N) client sorting per callback, including completed/cancelled history. A business-wide role with no selected branch reads all business bookings. The 15-second timeout changes UI state, not query size. `FlatList` virtualization in bookings/requests only limits rendered rows, not Firestore reads or the in-memory array.
2. Firestore bills listener additions and updates (and removals caused by a changed match) as document reads; reconnect can bill the initial result again depending on offline persistence. An empty query costs at least one read. For illustration, 5,000 vendor sessions each opening a 1,000-booking scope imply **5,000,000 initial document reads**, before reconnects or changes; this is a scenario, not a DAU forecast. A 50+1 page would initially return at most 51 booking documents per query, or 255,000 reads under the same session assumption, plus separately fetched pages and aggregate documents. A snapshot callback is not itself another full billed read, though it currently remaps the full result. See [Firestore billing](https://firebase.google.com/docs/firestore/pricing).
3. A naive `limit(50)` breaks semantics: `mobile/app/vendor/requests.tsx:31-35,49-51` sorts **all** Pending oldest-first and calls zero "all caught up"; `mobile/app/vendor/bookings.tsx:36-60` treats array and tab counts as exhaustive. `mobile/app/vendor/dashboard.tsx:70-95,121-175` derives open/pending/today/status/completed counts, completed value, and distinct customers from that same array. Calendar (`calendar.tsx:24,51,89-124`), customer history (`customer/[id].tsx:25-31,116-127`), and staff draft assignment counts (`staff.tsx:117`) also assume completeness. Booking detail, status update, and assign-staff routes look up only the array (`booking-detail/[id].tsx:37-42`, `status-update/[id].tsx:17-19`, `assign-staff/[id].tsx:19-24`), so a paged-out ID currently becomes "unavailable"; local invoice draft creation also requires array residency (`mobile/lib/store.ts:690-696`). `mobile/lib/vendor-feed-status.ts` has only loading/error/retry, not page completeness.
4. `mobile/lib/vendor-insights.ts:84-104` is a separate one-shot `limit(501)` analytics read that intentionally refuses totals when truncated; it is **not** a source for dashboard totals. Existing `firestore.indexes.json` has business/branch + bookingDate/status indexes but no composite for the proposed stable created-time pages. Rules at `firestore.rules:420-484` allow booking actors to read and some clients to update bookings directly; an API-only counter updater would miss those writes.

## Read design and screen contract

* Keep the tenant/role scope from the current hook: business-wide roles may select a branch or the whole business; other booking actors must query only an authorized branch. Include both `businessId == claim.b` and `branchId == selected authorized branch` for branch queries, with a matching rules-emulator test. Never use `assignedStaffId` to restrict the feed. Reset pages, counters, and detail cache synchronously on UID/claim/business/branch changes; do not persist server-owned booking data.
* Replace the all-bookings array contract with a scoped repository: 50-row pages ordered by normalized `createdAtSort desc`, stable document-ID tie-breaker, `limit(51)`, `startAfter(last DocumentSnapshot)`. Listen only to the first page while the vendor workspace is active; fetch later pages on demand, dedupe by booking ID, invalidate/reload pages on scope or ordering changes. `hasMore` comes from the 51st document, not from an aggregate. Status tabs query `status == selectedStatus` server-side, rather than filtering a partial All page. Show "loaded X of Y" or "more" where appropriate; never label a partial page as all bookings. The store can retain only currently loaded rows, but must not imply completeness.
* Make Requests its **own** `status == 'Pending'`, `createdAtSort asc`, 50+1 cursor stream, independent of All/history pages. Its first page contains the oldest actionable requests, preserving the current priority. Load successive pages until `hasMore == false`; do not cap total reachability or infer "all caught up" from an empty partial/cache result. Keep an exact pending counter for the header; when it changes after a page was loaded (including new requests beyond the oldest page), indicate newer work and refresh/continue pages rather than silently hiding it. On focus/pull-to-refresh and after a transition, restart the cursor chain; treat cached or pending-write snapshots as provisional, and surface failed later-page reads with retry without dropping already loaded rows. The inbox is complete in **reachability and count**, not by keeping every pending row subscribed. Do not make a live-head listener plus stale older pages claim an exact live list.
* Dashboard listens to scoped aggregate documents for exact status/open/pending/completed/customer/value totals, not the booking page. Fetch only five rows per displayed status column and five eligible rows for Qatar "today"; column counts come from aggregates. Calendar queries one selected Qatar day at a time and pages that day's rows. Customer history queries by `userId` (not display name) within the tenant scope and pages it; legacy name-only records require migration or an explicit incomplete-history state. Direct ID routes fetch `bookings/{id}` on demand, validate business/branch permission, and distinguish loading, not-found, and forbidden; do not depend on list-page residency. Route local invoice drafts through that fetched detail instead of a page-limited array lookup. The staff draft count must either use an exact per-staff active count or explicitly say "loaded jobs"; assignment is otherwise a separate workstream.
* Add immutable/queryable `createdAtSort` and `bookingDayId` (YYYY-MM-DD in Asia/Qatar), plus `scheduleVisible` for today's current exclusion of Cancelled/Declined/NoShow. Backfill legacy string/Timestamp/missing dates before flipping readers. `orderBy` omits documents missing its field, so a mere new query would silently lose old bookings ([Firestore ordering](https://firebase.google.com/docs/firestore/query-data/order-limit-data)). Preserve oldest-first request ordering with an explicit fallback for bad historical `createdAt`; do not use device `now` as a permanent sort key. A booking's scheduled day and visibility must be updated by every writer that changes booking date/status.

## Exact aggregate projection

Use server-owned, read-only-to-clients `vendor_booking_stats` per business scope and per branch scope. Fixed shards (start with 16, tune from measured write contention) hold status counts, open count, pending count, completed count, completed **cost in integer minor units**, invalid/nonpositive completed-cost count, and distinct-customer count. Separate Qatar-day shard documents hold day total, day pending, and day `scheduleVisible` total; selecting today's key avoids a midnight rewrite. Sum all shards only after each is loaded from server; never show a partial shard sum as a total. Reviews still come from the branch's existing `reviewCount`, not booking stats. Preserve dashboard "Unavailable" for completed value when any completed cost is absent/invalid/nonpositive or for customers when any booking lacks `userId`; maintain those invalid-input counts explicitly. Scope keys contain business/branch IDs, never staff IDs.

Maintain the projection on **every** booking create/update/delete with a Firestore write trigger, since writes currently come from `src/app/api/bookings/route.ts`, transition/quote/expiry routes, `mobile/lib/firestoreOps.ts:129-151` customer cancellation, and web direct SDK edits/deletes in `src/app/vendor/dashboard/bookings/page.tsx:255-337`. In one transaction, read the current booking document and a per-booking applied-state ledger, compute the delta from ledger state to current state, update the relevant business/branch/global/day shards and per-scope customer refcounts, then store the new ledger state. Deletion projects `null`. This makes duplicate or out-of-order trigger deliveries converge to the latest booking state; transaction retries serialize concurrent ledger changes. On customer refcount 0<->1, update distinct-customer count in the same transaction. Stable hash of booking ID chooses the counter shard; if scope/day changes, decrement the old scope/day and increment the new. The trigger must not write back to the booking. Monitor failed trigger executions and provide a replay/reconciliation job; "exact" means after projection catches up, not synchronous with a just-committed booking. Expose last-applied/update freshness and a loading/stale state, never silently substitute partial page counts. Enforce rules denying client writes to stats/ledgers and allowing only claimed business/branch readers; Firestore rules are not filters ([rules and queries](https://firebase.google.com/docs/firestore/security/rules-query)).

## Indexes and costs

Add collection-scope composites in `firestore.indexes.json` for **both** `businessId` and `branchId` prefixes (branch queries also carry businessId, so use `(businessId, branchId, ...)` for those):

* `createdAtSort DESC` for All; `status ASC, createdAtSort DESC` for status tabs/dashboard columns; `status ASC, createdAtSort ASC` for oldest-first Pending.
* `bookingDayId ASC, createdAtSort DESC` for Calendar and `bookingDayId ASC, scheduleVisible ASC, createdAtSort DESC` for today's dashboard rows.
* `userId ASC, createdAtSort DESC` under the tenant/branch prefix for customer history, if implemented client-side.

Use document-snapshot cursors (implicit `__name__` tie-breaker) and verify actual index requirements with emulator/Query Explain before deploy. Do not use offsets: they bill skipped documents. These are up to 12 composites for the six query shapes across business and branch scopes, unless a measured query/index can safely be shared. The current equality-only listener may use single-field indexes; the existing bookingDate composites do **not** serve `createdAtSort` order. Read budget is bounded per opened page/preview, not globally capped: a user who walks all N pages can still read N documents. An empty query has a one-read minimum; index-entry charges depend on query shape, and counters add 16 aggregate document reads per scoped refresh/listen plus trigger ledger/shard writes. Verify index-entry billing with Query Explain rather than assuming zero ([Firestore billing](https://firebase.google.com/docs/firestore/pricing)).

## Rollout, rollback, verification

1. Deploy indexes, rules, projection trigger and metrics first. Backfill normalized booking fields and replay every existing booking through the same idempotent ledger projector while live triggers run. Reconcile per-scope status totals, day totals, distinct customers, and completed value against server-side full scans, including writes/deletes during backfill; do not enable counters until each scope passes. Record trigger lag, contention/retries, failed events, document reads/session, page latency, and index build status.
2. Ship scoped mobile readers behind a remote kill switch: internal accounts, then a small cohort, then all vendors after read-cost and completeness checks. Switch dashboard totals only with a reconciled, fresh projection; keep loading/unavailable on missing stats instead of deriving false totals from partial pages. Web vendor listeners and 501-row mobile analytics cap are separate follow-on scale risks, not silently fixed by this mobile sidecar.
3. Roll back the **reader** switch to the existing full listener if pages/counters fail, leaving the projection/backfill running for repair; this restores correctness but also restores unbounded read cost, so use only as a temporary incident measure. Do not delete ledgers or stats on rollback. A projection-only rollback requires disabling counter display first; never resume page-limited UI with array-derived totals.

Tests to gate release: rules-emulator tenant/branch/role denial for page, detail and stats; index-backed first/next/last page with equal timestamps and legacy dates; 51/52+ Pending items, arrivals beyond page one, status transitions/deletes during pagination, offline/reconnect, and later-page failure with no false empty state; dashboard totals across >50 bookings and Qatar midnight; duplicate/out-of-order trigger delivery, concurrent writes, delete/recreate, scope/day/customer changes, invalid costs and missing customer IDs; backfill with live writes and reconciliation; deep links to paged-out bookings; branch/account switch cache purge; read-count load test at target vendor concurrency. Existing `mobile/__tests__/vendor-ui-flow.test.tsx`, `vendor-dashboard-truth.test.tsx`, `vendor-merge.test.ts`, `booking-feed.test.tsx`, `vendor-calendar.test.ts`, and rules tests are the nearest fixtures to extend. No staff-assignment behavior is changed by this plan.
